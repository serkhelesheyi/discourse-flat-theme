# ۷. گزارش امکان‌سنجی تقویم شمسی (جلالی) در Discourse

> **تاریخ:** ۲۰۲۶-۱۰-۲۴ · **وضعیت:** گزارش پژوهشی — هیچ کدی تغییر نکرده است.
>
> **پرسش مالک:** آیا می‌توان همهٔ تاریخ‌های میلادی انجمن را شمسی کرد؟ بهینه‌ترین راه «تبدیل در هنگام نمایش» است؟ چه ملاحظاتی دارد؟
>
> **روش:** خواندن سورس واقعی هستهٔ Discourse (شاخهٔ `main`) در همین تاریخ، بررسی مستندات و موضوع‌های Meta، و بررسی پروژه‌های فارسی موجود؛ به‌همراه یک بنچمارک واقعی برای هزینهٔ تبدیل. هیچ ادعای «امتحان کردم و دیدم» بدون شماره یا فایل نیست.

## ۱) حکم کوتاه

| پرسش | پاسخ |
|---|---|
| امکان دارد؟ | **بله.** تبدیل در لایهٔ نمایش کاملاً ممکن است و دیتابیس، API و جستجو دست‌نخورده می‌مانند. |
| با تم فعلی (بدون پلاگین) کامل می‌شود؟ | **نه.** تم هیچ hook عمومی برای فرمت تاریخ ندارد و هسته اسپن‌های تاریخ را با تایمر بازنویسی می‌کند (بند ۳-۳). با تم فقط بخش‌های خودِ تم و تعداد محدودی کامپوننت قابل تغییرند. |
| «تبدیل هنگام نمایش» بهینه‌ترین است؟ | **بله** — هم معماری (۰ بایت مهاجرت داده) و هم کارایی (۱٫۵۷µs برای هر تاریخ با formatter کش‌شده؛ بند ۵-۱۳). |
| مسیر پیشنهادی | یک پلاگین کوچک که در **یک نقطهٔ گلوگاه** خروجی تاریخ را شمسی می‌کند + یک هلپر سمت Ruby برای ایمیل‌ها. **بدون** فورک‌کردن فایل‌های هسته. |
| هزینهٔ تقریبی | اسپایک ۰٫۵–۱ روز، MVP رابط کاربری ۲–۳ روز، ایمیل ۱–۲ روز، سخت‌سازی و ماتریس تست ۲ روز (بند ۶). |

**نکتهٔ مهم:** تبدیل شمسی یک «ترجمه» نیست، تغییر تقویم است؛ سال، طول ماه و شمارهٔ روز همه عوض می‌شوند. پس هر جا تاریخ **ورودی** است (انتخابگر تاریخ، فیلتر جستجو، `[date]`) میلادی می‌ماند و فقط خروجی دیداری شمسی می‌شود؛ در غیر این صورت داده‌های اشتباه ذخیره می‌شوند.

## ۲) «همهٔ تاریخ‌ها» یعنی چه — نقشهٔ سطوح

| سطح | نمونه | موتور | با تبدیل لایهٔ نمایش پوشش می‌گیرد؟ |
|---|---|---|---|
| تاریخ‌های مطلق رابط | پروفایل (عضویت، آخرین فعالیت)، نشان‌ها، اعلان‌ها، بوکمارک، «آخرین ویرایش»، جدول‌های ادمین، فهرست کاربران | `moment` + رشته‌های `dates.*` (کلاینت) | ✅ بله |
| عمر نسبی | «۳ دقیقه پیش»، «دیروز» | `moment.fromNow` در همان فرمتر | ➖ تقویم ندارد؛ نیازی نیست |
| چت | زمان پیام، جداکنندهٔ روز | `format-chat-date` (مسیر جدا) | ✅ با پوشش همان نقطهٔ گلوگاه |
| انتخابگر تاریخ (ورودی) | تقویم کامپوزر، زمان‌بندی موضوع، `[date]`، رویدادها | `d-date-picker` / `d-date-time-input` | ❌ و **نباید** عوض شود |
| ایمیل و خلاصهٔ هفتگی | `short_date(post.created_at)` در `app/views/email/_post.html.erb` | Rails `I18n.l` + `time.formats` | ❌ سمت سرور است؛ تبدیل جدا لازم دارد |
| HTML خزنده/بدون JS | `?crawler=1`، پیش‌نمایش لینک | سمت سرور | ❌ مثل ایمیل |
| JSON API | `created_at`، `last_posted_at` | ISO 8601 | ✅ از قبل درست است؛ **نباید** عوض شود |
| فایل تقویم `.ics` | `calendar_ics: "%Y%m%dT%H%M%SZ"` | RFC 5545 | ❌ **ممنوع** — استاندارد iCalendar فقط میلادی می‌پذیرد |
| جستجو (`after:`، `before:`) | فیلترهای جستجو | رشتهٔ میلادی | ❌ ورودی است |

یعنی «همهٔ تاریخ‌ها» در عمل سه دسته است: **رابط (کلاینت)**، **ایمیل/سرور**، و **ماشین‌خوان (API/ICS)**. دو دستهٔ اول باید تبدیل شوند، دستهٔ سوم هرگز.

## ۳) شواهد از سورس هسته (چرا تم کافی نیست)

### ۳-۱) یک قیف واحد: `moment` + رشته‌های `dates.*`

`frontend/discourse/app/lib/formatter.js` تقریباً همهٔ تاریخ‌های مطلق را می‌سازد:

```js
export function shortDate(date) {
  return moment(date).format(i18n("dates.medium.date_year"));
}
export function tinyDateYear(date) {
  return moment(date).format(i18n("dates.tiny.date_year"));
}
export function longDate(dt) {
  return moment(dt).format(i18n("dates.long_with_year"));
}
```

و در `config/locales/client.fa_IR.yml` این رشته‌ها توکن‌های `moment` هستند:

```yaml
dates:
  long_with_year: "D MMMM، YYYY HH:mm"
  tiny:
    date_month: "D MMMM"
    date_year: "MMMM YYYY"
```

یعنی هسته در `fa_IR` **نام ماه فارسی** می‌دهد ولی تقویم **میلادی** است. همان وضعیت سمت سرور در `config/locales/server.fa_IR.yml` (`date.month_names` = ژانویه…دسامبر، `time.formats.short: "%m-%d-%Y"`).

### ۳-۲) API عمومی پلاگین هیچ hook تاریخ ندارد

`frontend/discourse/app/lib/plugin-api.gjs` (۴٬۰۲۵ خط) را جست‌وجو کردم: تنها مورد مرتبط با تاریخ `downloadCalendar` است. هیچ `registerDateFormatter` یا transformer تاریخ وجود ندارد. نتیجه: تبدیل کامل از مسیر تم ممکن نیست؛ یا باید نقطهٔ گلوگاه `moment` را پچ کرد (پلاگین)، یا فایل‌های هسته را جایگزین کرد (مسیر بد، بند ۴-د).

### ۳-۳) هسته اسپن‌های تاریخ را با تایمر بازنویسی می‌کند

```js
export function updateRelativeAge(elems) {
  elems.forEach((elem) => {
    elem.innerHTML = relativeAge(new Date(parseInt(elem.dataset.time, 10)), {
      format: elem.dataset.format,
      wrapInSpan: false,
    });
  });
}
```

هر تاریخ مطلق یک `<span class="relative-date" data-time="…" data-format="…">` است و این تابع (در `autoUpdatingRelativeAge` و جاب‌های دوره‌ای) `innerHTML` را از `data-time` بازسازی می‌کند. پس اگر تم با JavaScript متن تاریخ را شمسی کند، اولین tick آن را پاک می‌کند. این تنها دلیل فنی کافی برای ردکردن «تم‌فقط» است.

### ۳-۴) مسیرهای موازی که فراموش می‌شوند

| مسیر | فایل | نکته |
|---|---|---|
| هلپر قالب | `ui-kit/helpers/d-format-date.js` → `autoUpdatingRelativeAge` | همهٔ `<DDate>`/`format-date`ها از اینجا می‌گذرند |
| چت | `plugins/chat/.../helpers/format-chat-date.js` | مستقل از `formatter.js`؛ با `moment.tz(...).format(...)` |
| تاپیک تایم‌لاین و `period-title` | هلپرهای محلی | در پروژه‌های قدیمی جدا پچ می‌شدند |
| ایمیل | `app/views/email/_post.html.erb` → `short_date(post.created_at)` | Rails، نه JavaScript |

### ۳-۵) باگ بالقوه‌ای که تبدیل شمسی به آن برمی‌خورد

```js
export function smartShortDate(date, withYear = tinyDateYear) {
  return date.getFullYear() === new Date().getFullYear()
    ? shortDateNoYear(date)
    : withYear(date);
}
export function longDateNoYear(dt) {
  if (new Date().getFullYear() !== dt.getFullYear()) { … }
}
```

این مقایسه‌ها با **سال میلادی** انجام می‌شوند. اگر نمایش شمسی شود، بین ۱ ژانویه و ۲۰ مارس (۱۰–۱۱ دی تا ۳۰ اسفند) سال شمسی هنوز عوض نشده اما مقایسه میلادی سال را عوض‌شده می‌بیند؛ نتیجه: سال در جایی حذف یا اضافه می‌شود که نباید. هر پیاده‌سازی شمسی باید این توابع را هم هم‌زمان در نظر بگیرد.

## ۴) مسیرهای اجرایی و مقایسه

### الف) تم/کامپوننت فقط

- **چه می‌شود:** بلوک‌های خود تم (مثل `block-rail-events` که همین حالا تاریخ را با `Intl` می‌سازد)، و با `modifyClass` شاید چند کامپوننت.
- **چه نمی‌شود:** بقیهٔ رابط، چون هیچ hook تاریخ در `plugin-api` نیست و تایمر هسته خروجی را بازنویسی می‌کند.
- **داوری:** ✅ برای «همان چند بلوک تم»، ❌ به‌عنوان راه‌حل «همهٔ تاریخ‌ها».

### ب) پلاگین + `Intl` (بدون وابستگی، ۰ بایت کتابخانه)

مرورگرها تقویم شمسی را بومی دارند: `new Intl.DateTimeFormat("fa-IR", { calendar: "persian", … })` → «۱۱ دی ۱۴۰۴».

- **مزیت:** صفر وابستگی، نام ماه و ارقام بومی، به‌روزرسانی خودکار با ICU مرورگر، سازگار با هر زبانی که بعداً اضافه شود.
- **هزینه:** نسخهٔ فعلی هسته از `moment` استفاده می‌کند نه `Intl`؛ پس باید یک **لایهٔ نگاشت توکن** بنویسیم (`YYYY/MM/DD/MMMM/HH:mm` → اجزای `Intl`) و در نقطهٔ گلوگاه (پچ `moment.fn.format` یا جایگزینی خروجی فرمتر) اعمال کنیم. کار متوسط، ولی تمیزترین نتیجه.
- **ریسک:** توکن‌های خاص moment مثل `Do`، `LT`، `calendar()` و `fromNow()` باید صریح مدیریت شوند (بند ۵).

### ج) پلاگین + `moment-jalaali` (۴۱٫۶KB، MIT، ۹۷۴★، آخرین push اوت ۲۰۲۶)

- **مزیت:** همان API هسته، با توکن‌های `jYYYY/jMM/jD`؛ `moment.tz`، طول ماه جلالی، سال کبیسه و `jYear()` همه آماده؛ فاصله از رفتار هسته کمترین است.
- **هزینه:** باید **قبل از** جاوااسکریپت اپ لود شود (`register_asset "…", :server_side`) تا `moment` را پچ کند؛ سپس رشته‌های `dates.*` هم باید j-token شوند (یا از طریق locale پلاگین، یا با نگاشت در همان نقطهٔ گلوگاه).
- **ریسک:** پچ کردن `moment` سراسری است؛ هر کدی در هسته یا پلاگین‌های دیگر که به توکن میلادی تکیه کند تحت تأثیر قرار می‌گیرد (باید با تست پوششی کنترل شود).

### د) جایگزینی فایل‌های هسته (روش پروژه‌های فارسی موجود)

تنها پروژهٔ عمومی موجود، `l3est/discourse-jalali` است؛ دستور نصبش در README این است:

```bash
cp ~/discourse-jalali/app/assets/javascripts/discourse/lib/formatter.js.es6 \
   ~/discourse/app/assets/javascripts/discourse/lib/formatter.js.es6
```

و داخل آن فایل، خطوط هسته کامنت و با `moment(dt).format("jD jMMMM jYYYY HH:mm")` جایگزین شده است. آخرین push آن **۲۰۲۰** است و برای نسخه‌های امروز کار نمی‌کند. این مسیر با هر ارتقاء هسته می‌شکند و **رد** می‌شود.

### جدول مقایسه

| مسیر | پوشش «همهٔ تاریخ‌های رابط» | حجم | ریسک | نگهداری |
|---|---|---|---|---|
| الف) تم فقط | ~۳۰٪ (خود تم) | ۰ | کم ولی ناکافی | ساده |
| ب) پلاگین + `Intl` | ۱۰۰٪ با نگاشت توکن | ۰ (بومی مرورگر) | متوسط | خوب — بدون وابستگی خارجی |
| ج) پلاگین + `moment-jalaali` | ۱۰۰٪ با j-token | ~۴۲KB | متوسط تا بالا (پچ سراسری moment) | وابسته به یک کتابخانهٔ فعال |
| د) فورک فایل‌های هسته | ۱۰۰٪ تا اولین ارتقاء | — | **بحرانی** | فاجعه |

## ۵) ملاحظات دقیق (چک‌لیست اجرایی)

1. **یک نقطهٔ گلوگاه، نه چند نقطه.** هر تاریخ مطلق رابط از `autoUpdatingRelativeAge`/`d-format-date` می‌گذرد. تبدیل باید همان‌جا (یا در `moment.fn.format` که زیربنای آن است) انجام شود؛ پچ‌کردن تک‌تک کامپوننت‌ها نگهداری‌ناپذیر است.
2. **تایمر `updateRelativeAge`.** تبدیل باید در تولید رشته باشد نه در DOM؛ وگرنه هر tick پاک می‌شود (بند ۳-۳).
3. **سرکوب سال.** `smartShortDate` و `longDateNoYear` سال را با `getFullYear()` میلادی مقایسه می‌کنند؛ باید با سال شمسی مقایسه شوند، وگرنه در دی–اسفند سال اشتباه حذف/نمایش داده می‌شود (بند ۳-۵).
4. **توکن‌های خاص.** `Do` (پسوند ترتیبی)، `LT`/`LTS` (فرمت زمان locale)، `calendar()` (امروز/دیروز/هفتهٔ بعد)، `fromNow()` (نسبی) و `until()` (زمان‌بندی) هرکدام رفتار جدا دارند؛ نسبی‌ها باید دست‌نخورده بمانند و فقط تاریخ‌های تقویمی تبدیل شوند.
5. **ارقام.** یا همه از `Intl` (ارقام فارسی خودکار) یا همه از `dNumber`؛ دو منبع عددسازی در یک صفحه، ناسازگاری می‌سازد (همین اشتباه در بلوک رویدادهای تم ما یک بار رخ داد و اصلاح شد).
6. **منطقهٔ زمانی و مرز روز.** تبدیل جلالی باید **بعد** از اعمال منطقهٔ زمانی کاربر انجام شود؛ یک لحظهٔ UTC می‌تواند در تهران یک روز و در لندن روز قبل باشد. مرزهای نوروز و ماه‌های ۳۱روزه همین‌جا معنا پیدا می‌کنند. توجه: ایران از ۲۰۲۲ ساعت تابستانی ندارد، ولی تاریخ‌های قدیمی‌تر در `Asia/Tehran` هنوز DST دارند و کتابخانه باید درست عمل کند.
7. **ورودی‌ها میلادی می‌مانند.** انتخابگر تاریخ، زمان‌بندی موضوع، `[date=…]`، رویدادها و فیلترهای جستجو با ISO کار می‌کنند. اگر نمایش شمسی شود ولی ورودی میلادی بماند، کاربر دو تقویم را هم‌زمان می‌بیند؛ راه‌حل استاندارد: نمایش شمسی + `title`/tooltip با تاریخ میلادی و ISO در `data-time` (که هسته از قبل دارد).
8. **ایمیل و خلاصهٔ هفتگی سمت سرور.** `short_date(post.created_at)` در `app/views/email/_post.html.erb` و `time.formats` در `server.fa_IR.yml` با Rails کار می‌کنند؛ نیاز به یک هلپر Ruby (مثلاً بر پایهٔ gem `parsi-date` یا تابع تبدیل خودمان) و رشته‌های `%-d %B` شمسی دارد. بدون این، ایمیل‌ها میلادی می‌مانند و کاربر دو رفتار متفاوت می‌بیند.
9. **HTML خزنده و پیش‌نمایش لینک.** همان وضعیت ایمیل: سمت سرور رندر می‌شود؛ برای یکدستی کامل باید سمت Rails هم تبدیل شود.
10. **API، ICS و `data-*`.** `created_at` در JSON باید ISO بماند (کلاینت‌های دیگر، اپ موبایل، و ابزارها به آن تکیه می‌کنند). `calendar_ics` باید میلادی بماند (RFC 5545). `data-time` باید timestamp بماند تا تایمر هسته کار کند.
11. **جستجو و مرتب‌سازی.** `after:`/`before:` و مرتب‌سازی‌ها با epoch کار می‌کنند و نباید تغییر کنند؛ فقط نمایش شمسی می‌شود. (اگر روزی «جستجوی تاریخ شمسی» خواستید، آن یک قابلیت جدا با تبدیل ورودی است.)
12. **انجمن چندزبانه.** اگر سایت `fa_IR` است ولی کاربری زبان انگلیسی انتخاب کرده، باید تاریخ برای او میلادی بماند. تصمیم: تبدیل بر اساس locale کاربر (نه تنظیم سایت) — و همان `I18n.currentBcp47Locale` که در ۳٫۲٫۰ برای بلوک رویدادها استفاده شد، همین را می‌دهد.
13. **کارایی — اندازه‌گیری واقعی.** با یک formatter کش‌شده: **۱٫۵۷µs برای هر تاریخ** (۱۰٬۰۰۰ تاریخ در ۱۵٫۷ms). با ساختن formatter در هر فراخوانی: **۱۵۸µs برای هر تاریخ** (۱۰٬۰۰۰ تاریخ در ۱٫۵۸ ثانیه، یعنی ۱۰۰ برابر کندتر). نتیجه: ساخت یک‌بار و کش به‌ازای locale، الزامی است. با `moment-jalaali` هم تبدیل فقط روی تاریخ‌های نمایش‌داده‌شده اجرا می‌شود، نه روی همهٔ دیتابیس.
14. **دسترسی‌پذیری.** متن شمسی خوانده می‌شود ولی `datetime`/`data-time` میلادی می‌ماند؛ برای صفحه‌خوان و ابزارها این بهترین حالت است. در tooltip بهتر است هر دو تقویم بیاید («۲ آبان ۱۴۰۵ — ۲۴ اکتبر ۲۰۲۶»).
15. **تست‌های لازم.** اسفند ۳۰ در سال کبیسه (۱۴۰۳)، نوروز (مرز سال)، ۲۹/۳۰/۳۱ روزه بودن ماه‌ها، سال‌های قبل از ۱۳۰۰، DST تاریخی تهران، تغییر locale در میانهٔ نشست، و `prefers-reduced-motion` (بی‌ربط ولی در ماتریس فاز ۶ هست).
16. **نگهداری.** هر دو مسیر ب و ج به رفتار داخلی `moment` وابسته‌اند؛ اگر Discourse روزی موتور تاریخش را عوض کند (مثلاً به `Intl` مهاجرت کند)، پلاگین باید بازبینی شود. مسیر ب (Intl) در آن سناریو آیندهٔ بهتری دارد.

## ۶) برآورد و فازبندی پیشنهادی

| فاز | کار | خروجی قابل سنجش | تخمین |
|---|---|---|---|
| ۰ | اسپایک روی یک Discourse واقعی: پچ `moment.fn.format` در کنسول و مشاهدهٔ ۱۰ نقطهٔ مختلف | فهرست دقیق مسیرهایی که پوشش می‌گیرند/نمی‌گیرند | ۰٫۵–۱ روز |
| ۱ | پلاگین حداقلی کلاینت (تبدیل تاریخ‌های مطلق، نسبی‌ها دست‌نخورده) + کش formatter | `/latest`، موضوع، پروفایل، اعلان‌ها با تاریخ شمسی | ۲–۳ روز |
| ۲ | پوشش چت، تایم‌لاین، `local-dates`، ادمین | همان صفحات در `fa_IR` | ۱ روز |
| ۳ | ایمیل و خلاصهٔ هفتگی (هلپر Ruby) | یک ایمیل واقعی با تاریخ شمسی | ۱–۲ روز |
| ۴ | ماتریس تست (کبیسه/نوروز/مناطق زمانی) + مستندسازی + بازبینی `safe-mode` | جدول نتایج در `docs/` | ۲ روز |

**معیار پذیرش:** هیچ تاریخ میلادی در رابط `fa_IR` نمانده باشد؛ API/ICS/`data-time` دست‌نخورده؛ در locale غیرفارسی هیچ تغییری نباشد؛ و در `safe-mode` همه چیز به حالت عادی برگردد.

## ۷) توصیهٔ نهایی

1. **داده را هرگز تبدیل نکنید.** تبدیل در لایهٔ نمایش درست‌ترین و بهینه‌ترین انتخاب است؛ مهاجرت دیتابیس به شمسی، مرتب‌سازی، API، ICS و جستجو را می‌شکند و برگشت‌پذیر نیست.
2. **با تم به‌تنهایی دنبال «همهٔ تاریخ‌ها» نروید.** پوشش ناقص می‌ماند و تایمر هسته آن را پاک می‌کند.
3. **اگر تصمیم به اجرا گرفتید، مسیر ب (`Intl`) را پیشنهاد می‌کنم:** صفر وابستگی، آیندهٔ بهتر، و همان مسیری که در ۳٫۲٫۰ برای بلوک رویدادها استفاده شد (با تفاوت `calendar: "persian"`). اگر می‌خواهید کمترین انحراف از رفتار امروز هسته را داشته باشید و از پچ توکن نترسید، مسیر ج (`moment-jalaali`) بالغ‌ترین کتابخانهٔ موجود است.
4. **قبل از هر کاری، فاز ۰ (اسپایک) را روی نسخهٔ واقعی انجمن اجرا کنید؛** بدون آن، عددهای پوشش حدس است. این گزارش عمداً هیچ‌کدام از مسیرها را «تأییدشده روی نمونهٔ زنده» اعلام نمی‌کند.
5. **تصمیم محصولی که باید بگیرید:** آیا تاریخ شمسی برای همهٔ کاربران انجمن (فارسی‌زبان) است یا فقط وقتی locale کاربر `fa_IR` است؟ پیشنهاد: دومی.
